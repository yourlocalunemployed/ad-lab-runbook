How to read this

All of the commands here were obtained through a class lecture — the commands themselves, and the order they run in, come from a taught Windows Server course. The explanation above each command, the structure, and the corrections were added afterwards.

Nearly all of PowerShell is guessable once you know the verb. The verb tells you what a command does to the world; the noun tells you what it does it to.

Get-Just look. Never changes anything — safe to run any time.
New-Create something that doesn't exist yet.
Set-Change something that already exists.
Add-Put something into something else.
Install-Install a Windows feature or role.
Import-Load a toolbox of commands into this session.
Resolve-Ask DNS a question.
Remove-Delete. Not used here — worth knowing it exists.
|Pipe. Take what came out of the left and feed it into the right.
`Backtick at the end of a line: this command continues on the next line. Nothing may follow it — not even a space.
$xVariable. A box you put something in and reuse later.
@( )Array. A numbered list of things.
@{ }Hashtable. A list of Name = Value pairs, like one row of a form.
DNDistinguished Name. An object's full address, read right to left: OU=Finance,OU=LAB-Users,DC=contoso,DC=com

24 things in the notes that don’t work

Every command below is reproduced here exactly as it was written in class, mistakes included, and flagged where it appears. The downloadable .ps1 has all 24 corrected and marked with a # FIXED: comment. These are the ones worth knowing about:

  1. Four stop the script dead. A missing $ on UserGPO =; curly “ ” quotes from a Word paste in three LDAP filters; "audit. Test" and "recycle. Test" with a stray space; and the words Unlock an account sitting on a line as if they were a command.
  2. Two fail silently — the dangerous kind. Misplaced brackets mean New-GPLink never runs, so the workstation GPO is created but never linked and does nothing at all. And SchemaMastGet-NetAdapterer just returns an empty column.
  3. Four error out when you reach them. The two DL-FinanceShare-* groups get members added but are never created; Export-Csv writes to a folder that may not exist; gpresult /h needs an output path; whomai is a typo.
  4. One is the worst in the set. $UsersOU gets silently redefined to a single department OU partway through, so every later command using it targets the wrong place. Nothing errors — the wrong thing just quietly happens.
  5. Thirteen are consistency problems. Mostly hardcoded domains (contoso.com and lab.local both appear) and $InitialPassword being reused twice, each time overwriting the secure string from Part 5.
01

Look — what am I connected to?

Pure read-only. Getting your bearings before touching anything.

What version of PowerShell is this? First thing to check — older versions are missing commands you'll want.

$PSVersionTable

The full profile of this domain, and of the forest that contains it. Both dump a lot; the trimmed versions below are the readable ones.

Get-ADDomain
Get-ADForest

Same thing, but only the columns that matter. DomainMode is the feature level, set by your oldest domain controller's Windows version. The last three are FSMO roles.

Get-ADDomain |
   Select-Object DNSRoot, NetBIOSName, DistinguishedName,
       DomainMode, PDCEmulator, RIDMaster, InfrastructureMaster
FSMO

Five special jobs that only one domain controller can hold at a time: PDCEmulator, RIDMaster, InfrastructureMaster, SchemaMaster and DomainNamingMaster. Knowing which DC holds which is one of those things you only need at 2am, and then you need it badly.

Forest level. GlobalCatalogs are the DCs holding a searchable summary of every object in the forest.

Get-ADForest |
   Select-Object Name, RootDomain, ForestMode,
       SchemaMastGet-NetAdapterer, DomainNamingMaster, GlobalCatalogs
Left as typed

SchemaMastGet-NetAdapterer is a paste accident — it should be SchemaMaster. As written the column returns empty rather than erroring.

02

Store — put the details in variables

You're about to type the domain address dozens of times. Store it once.

Every later command can now just say $DomainDN. Run this in a different domain and nothing below needs editing — which is the real reason to bother.

Grab the whole domain and forest objects once, then pull the three useful fields out. The dot means reach inside this object and get that one property.

$Domain = Get-ADDomain
$Forest = Get-ADForest

$DomainName = $Domain.DNSRoot              # contoso.com
$DomainDN   = $Domain.DistinguishedName    # DC=contoso,DC=com
$NetBIOS    = $Domain.NetBIOSName          # CONTOSO
Easy to get caught by

Variables only live as long as the PowerShell window. Close it, reopen, and you must re-run this part before anything from Part 4 onwards will work — otherwise $DomainDN is empty and your OUs get created in strange places, or not at all.

03

Survey — what's installed, what's already here?

Checking your tools are present, and taking the "before" picture.

Every domain controller in the domain. IsGlobalCatalog tells you whether this DC holds the forest-wide index.

Get-ADDomainController -Filter * |
   Format-Table HostName, IPv4Address, Site, IsGlobalCatalog, OperationMasterRoles

Everything installed on this server. Reads as: get all features → keep the installed ones → sort → show as a table.

Get-WindowsFeature |
   Where-Object InstallState -eq "Installed" |
   Sort-Object Name |
   Format-Table DisplayName, Name

Check the four that matter, then install the two management toolsets. This is the first command in the whole script that changes the server.

Get-WindowsFeature AD-Domain-Services, DNS, RSAT-AD-Tools, GPMC

Install-WindowsFeature RSAT-AD-Tools, GPMC -IncludeManagementTools

Load the command sets. Modern PowerShell usually does this for you — doing it by hand means you get a clear error now rather than a confusing one later.

Import-Module ActiveDirectory
Import-Module GroupPolicy

Get-Module ActiveDirectory, GroupPolicy

The "before" snapshot — OUs, users and computers as they stand right now. Come back and run these again at the end to see your work.

Get-ADOrganizationalUnit -Filter * |
   Select-Object Name, DistinguishedName |
   Sort-Object DistinguishedName

Get-ADUser -Filter * |
   Select-Object Name, SamAccountName, Enabled |
   Sort-Object Name

Get-ADComputer -Filter * |
   Select-Object Name, Enabled, DistinguishedName

The legacy tool that prints which DC holds each of the five FSMO roles. Not PowerShell, but it's the fastest way to see all five at once.

netdom query fsmo

The DNS checks — pay attention to these. A domain controller must point at DNS that knows about the domain.

Get-DnsClientServerAddress -AddressFamily IPv4

Get-DnsServerZone

Resolve-DnsName "_ldap._tcp.dc._msdcs.contoso.com" -Type SRV
Resolve-DnsName "_kerberos._tcp.contoso.com" -Type SRV
Why the SRV records matter

Clients find domain controllers by asking DNS for these records — they're signposts saying "the DC lives here" and "go here to authenticate". No answer means nobody can log in, no matter what else you've configured correctly.

When someone says Active Directory is broken, it is nearly always DNS.

04

Build — create the OU structure

The filing cabinet comes before the files.

An OU is a folder inside AD. Users, groups and computers all need a -Path saying where to put them, and that path is an OU. The reason OUs actually matter, though, is that Group Policy links to them — which is what Part 9 depends on.

The pattern that repeats six times

Every block in this part is the same shape:

if (-not (Get-ADOrganizationalUnit ...)) { New-ADOrganizationalUnit ... }

"If looking for it does not find it, create it." That makes the script safe to re-run — run it twice and the second run creates nothing and errors on nothing. It's called being idempotent, and it's the habit that separates a script from a one-off.

Build each OU's full address up front, so later commands just say $UsersOU. Each one ends in $DomainDN, so it resolves to OU=LAB-Users,DC=contoso,DC=com.

$AdminsOU          = "OU=LAB-Admins,$DomainDN"
$UsersOU           = "OU=LAB-Users,$DomainDN"
$ComputersOU       = "OU=LAB-Computers,$DomainDN"
$GroupsOU          = "OU=LAB-Groups,$DomainDN"
$ServiceAccountsOU = "OU=LAB-Service-Accounts,$DomainDN"
$TestObjectsOU     = "OU=LAB-Test-Objects,$DomainDN"

The six top-level OUs, then the loop that creates them. $OU is "the current one" on each pass.

$TopLevelOUs = @(
    "LAB-Admins",
    "LAB-Users",
    "LAB-Computers",
    "LAB-Groups",
    "LAB-Service-Accounts",
    "LAB-Test-Objects"
)

foreach ($OU in $TopLevelOUs) {
    if (-not (Get-ADOrganizationalUnit `
        -LDAPFilter "(ou=$OU)" `
        -SearchBase $DomainDN `
        -SearchScope OneLevel `
        -ErrorAction SilentlyContinue)) {

        New-ADOrganizationalUnit `
            -Name $OU `
            -Path $DomainDN `
            -ProtectedFromAccidentalDeletion $true
    }
}
The switches, decoded

-SearchScope OneLevel looks only one level down, not the whole tree. -ErrorAction SilentlyContinue means "not found" is expected, don't shout about it. -ProtectedFromAccidentalDeletion ticks the box that stops someone deleting the OU by mistake.

The next five blocks are the same pattern aimed one level deeper each time. Rather than repeat them, here's what they build:

contoso.com ├─ LAB-Admins │ ├─ Tier-0 domain admins — the crown jewels │ ├─ Tier-1 server admins │ └─ Tier-2 helpdesk / workstations ├─ LAB-Users │ ├─ Finance │ ├─ Human Resources │ ├─ Information Technology │ ├─ Sales │ ├─ Contractors │ └─ Disabled Users where leavers get parked, not deleted ├─ LAB-Computers │ ├─ Workstations │ │ ├─ Sydney split by site so GPO can differ per office │ │ └─ Melbourne │ ├─ Servers │ └─ Quarantine somewhere to drop a suspect machine ├─ LAB-Groups │ ├─ Role Groups "who you are" │ └─ Resource Groups "what you can reach" ├─ LAB-Service-Accounts built, not used yet └─ LAB-Test-Objects built, not used yet
The deeper blocks, in full

Department OUs inside LAB-Users — note -SearchBase and -Path become $UsersOU instead of $DomainDN.

$DepartmentOUs = @(
  "Finance",
   "Human Resources",
   "Information Technology",
   "Sales",
  "Contractors",
   "Disabled Users"
)

foreach ($OU in $DepartmentOUs) {
   if (-not (Get-ADOrganizationalUnit `
       -LDAPFilter "(ou=$OU)" `
       -SearchBase $UsersOU `
       -SearchScope OneLevel `
       -ErrorAction SilentlyContinue)) {

      New-ADOrganizationalUnit `
           -Name $OU `
           -Path $UsersOU `
          -ProtectedFromAccidentalDeletion $true
   }
}

A shorter style for the rest — pipe the list into ForEach-Object, where $_ means "the current item". Same job as the loop above.

"Tier-0", "Tier-1", "Tier-2" | ForEach-Object {
   if (-not (Get-ADOrganizationalUnit `
       -LDAPFilter "(ou=$_)" `
       -SearchBase $AdminsOU `
       -SearchScope OneLevel `
       -ErrorAction SilentlyContinue)) {

      New-ADOrganizationalUnit `
           -Name $_ `
           -Path $AdminsOU `
          -ProtectedFromAccidentalDeletion $true
   }
}

# identical shape, aimed at $ComputersOU
"Workstations", "Servers", "Quarantine" | ForEach-Object { ... }

# three levels deep — build the address first, then the two city OUs
$WorkstationsOU = "OU=Workstations,$ComputersOU"
"Sydney", "Melbourne" | ForEach-Object { ... }

# and the two group OUs — see the AGDLP note in Part 7
"Role Groups", "Resource Groups" | ForEach-Object { ... }

Checkpoint. Sorting by DistinguishedName makes children appear directly under their parents, so the structure reads in order.

Get-ADOrganizationalUnit `
   -Filter * `
   -SearchBase $DomainDN |
   Sort-Object DistinguishedName |
   Format-Table Name, DistinguishedName
05

Defaults & password policy

Two commands that quietly fix a real problem.

Out of the box, anything joining the domain lands in the built-in Computers and Users containers. Those are containers, not OUs — and you cannot link Group Policy to them. So anything landing there gets none of your policy. These two commands fix that permanently.

New machines joining the domain now land in your Workstations OU; new users in your LAB-Users OU.

redircmp "OU=Workstations,OU=LAB-Computers,$DomainDN"

redirusr "OU=LAB-Users,$DomainDN"

# confirm — these two fields should now show YOUR OUs
Get-ADDomain |
   Select-Object UsersContainer, ComputersContainer

Ask for a password once and hold it in memory. -AsSecureString hides it as you type and keeps it encrypted, instead of sitting in the script as plain text.

$InitialPassword = Read-Host `
   "Enter an initial password for the sample users" `
   -AsSecureString

Get-ADDefaultDomainPasswordPolicy
Check the policy before you create users

If your chosen password fails the domain's length or complexity rules, New-ADUser rejects it — and the error message doesn't make it obvious that the password was the problem.

06

Users — create the people

Data separated from logic: a list, then one loop that reads it.

To add a person you add a block to the list and re-run. You never touch the creation code — which is the whole reason it's built this way.

Each @{ } is one person, like one row of a spreadsheet. SamAccountName is the login name; OU is which folder they get filed into.

$Users = @(
   @{
       GivenName       = "Sarah"
       Surname         = "Malik"
      SamAccountName  = "sarah.malik"
      Department      = "Finance"
       Title           = "Senior Accountant"
       Office          = "Sydney"
      EmployeeID      = "LAB1001"
       OU              = "OU=Finance,$UsersOU"
   },
   # ... james.wong, priya.sharma, daniel.nguyen,
   #     emily.taylor, michael.chen, alex.contractor
)

Create each one, skipping any that already exist. The $( ) lets you drop a property inside a string.

foreach ($User in $Users) {
   $ExistingUser = Get-ADUser `
       -Filter "SamAccountName -eq '$($User.SamAccountName)'" `
       -ErrorAction SilentlyContinue

   if (-not $ExistingUser) {
       $DisplayName = "$($User.GivenName) $($User.Surname)"
       $UPN = "$($User.SamAccountName)@$DomainName"

       New-ADUser `
           -Name $DisplayName `
          -DisplayName $DisplayName `
           -GivenName $User.GivenName `
           -Surname $User.Surname `
          -SamAccountName $User.SamAccountName `
          -UserPrincipalName $UPN `
          -Department $User.Department `
           -Title $User.Title `
           -Office $User.Office `
          -EmployeeID $User.EmployeeID `
           -Path $User.OU `
          -AccountPassword $InitialPassword `
           -Enabled $true `
          -ChangePasswordAtLogon $true
   }
}
Always set ChangePasswordAtLogon

It forces a new password on first sign-in, so you never know the user's real one. That's the difference between issuing a credential and sharing one.

Checkpoint. -Properties is needed because AD only returns a few fields by default — Department, Title, Office and EmployeeID have to be asked for explicitly.

Get-ADUser `
   -Filter * `
   -SearchBase $UsersOU `
   -Properties Department, Title, Office, EmployeeID |
   Select-Object Name, SamAccountName, Department, Title, Office, Enabled |
   Sort-Object Department, Name |
   Format-Table -AutoSize

Set the org chart. -Manager needs the manager's actual AD object, not a name string — so fetch them into a variable first.

$James = Get-ADUser "james.wong"

Set-ADUser `
    -Identity "sarah.malik" `
    -Manager $James

# prove it stuck — Manager isn't returned by default, so ask for it
$Sarah = Get-ADUser "sarah.malik" -Properties Manager

Get-ADUser $Sarah.Manager |
   Select-Object Name, SamAccountName, Title

Daniel's second account, for admin work only. Note -Path puts it in Tier-1, away from the regular staff.

New-ADUser `
   -Name "Daniel Nguyen - Server Admin" `
   -SamAccountName "adm-daniel.nguyen" `
   -UserPrincipalName "adm-daniel.nguyen@$DomainName" `
   -Description "Dedicated Tier 1 server administration account" `
   -Path "OU=Tier-1,$AdminsOU" `
   -AccountPassword $AdminPassword `
   -Enabled $true `
  -ChangePasswordAtLogon $true
Why two accounts for one person

You do your day job — email, browsing — as your normal account, and only use the adm- account when you actually need the extra rights. If the daily account gets phished, the attacker gets a normal user, not an admin.

07

Groups — create them, then fill them

Built entirely around one model. Learn the model and the rest is obvious.

You never give a permission to a person. When someone joins Finance you add them to one group and they inherit everything. When the share's permissions change you edit one group, not fifty users.

Group scopes — the bit that trips people up

Global holds users from this domain. Use it for "who you are".
Domain Local grants access to a resource in this domain. Use it for "what you can reach".
Universal spans the whole forest. Use it across multiple domains.

Separately, Security groups can be given permissions; Distribution groups are email lists only.

The role groups — the "G" of AGDLP. The GG- prefix means anyone reading the list instantly knows the scope.

$GlobalGroups = @(
    @{ Name = "GG-Finance-Employees";         Description = "All Finance employees" },
    @{ Name = "GG-HR-Employees";              Description = "All Human Resources employees" },
    @{ Name = "GG-IT-Employees";              Description = "All Information Technology employees" },
    @{ Name = "GG-Sales-Employees";           Description = "All Sales employees" },
    @{ Name = "GG-Sydney-Users";              Description = "Users based in Sydney" },
    @{ Name = "GG-Melbourne-Users";           Description = "Users based in Melbourne" },
    @{ Name = "GG-Server-Administrators";     Description = "Tier 1 server administrators" },
    @{ Name = "GG-Helpdesk-Password-Reset";   Description = "Delegated password resets" },
    @{ Name = "GG-Privileged-Password-Policy"; Description = "Privileged password policy" }
)

foreach ($Group in $GlobalGroups) {
    if (-not (Get-ADGroup `
        -Filter "Name -eq '$($Group.Name)'" `
        -ErrorAction SilentlyContinue)) {

        New-ADGroup `
            -Name $Group.Name `
            -SamAccountName $Group.Name `
            -GroupCategory Security `
            -GroupScope Global `
            -Path $RoleGroupsOU `
            -Description $Group.Description
    }
}

Now the "A" — put the accounts into the global groups. People end up in both a department group and a site group. That's the point: they stack.

Add-ADGroupMember `
   -Identity "GG-Finance-Employees" `
   -Members "sarah.malik", "james.wong"

Add-ADGroupMember `
   -Identity "GG-Sydney-Users" `
   -Members "sarah.malik", "james.wong",
           "daniel.nguyen", "michael.chen",
           "alex.contractor"

# ...and the same for HR, IT, Sales, Melbourne and Server-Administrators

Three ways to ask about membership, and they don't give the same answer.

# who is DIRECTLY in this group?
Get-ADGroupMember "GG-Finance-Employees"

# same, but expand any groups nested inside it
Get-ADGroupMember -Identity "GG-Finance-Employees" -Recursive

# the reverse: what groups is this PERSON in?
Get-ADPrincipalGroupMembership "sarah.malik" |
   Select-Object Name, GroupScope |
   Sort-Object Name

# the best one: every level of nesting, plus built-ins.
# this is what the user's access ACTUALLY is.
Get-ADAccountAuthorizationGroup "sarah.malik" |
   Select-Object Name, GroupScope |
   Sort-Object Name

The "DL" step — put the global groups into domain local groups. Note the members here are groups, not people.

Add-ADGroupMember `
   -Identity "DL-FinanceShare-Modify" `
   -Members "GG-Finance-Employees"

Add-ADGroupMember `
   -Identity "DL-FinanceShare-Read" `
   -Members "GG-IT-Employees"
These two groups are never created

Nothing in the script runs New-ADGroup for DL-FinanceShare-Modify or DL-FinanceShare-Read, so both lines above fail with "Cannot find an object with identity". Add this first:

New-ADGroup -Name "DL-FinanceShare-Modify" `
    -SamAccountName "DL-FinanceShare-Modify" `
    -GroupCategory Security -GroupScope DomainLocal `
    -Path $ResourceGroupsOU

$ResourceGroupsOU is defined at the top of this part and otherwise never used — this is what it was for.

08

Computers — the machine accounts

Every computer that joins a domain gets an account, exactly like a user.

Pre-creating them — "staging" — means the machine lands in the right OU and gets the right Group Policy from its very first boot, instead of appearing in the default container and having to be moved afterwards.

The machine list, same spreadsheet-row shape as the users. The naming convention is SITE-OS-NUMBER, so SYD-WIN11-01 reads at a glance.

$Computers = @(
    @{ Name = "SYD-WIN11-01"; Path = $SydneyWorkstationsOU;    Description = "Sydney Windows 11 lab workstation" },
    @{ Name = "SYD-WIN11-02"; Path = $SydneyWorkstationsOU;    Description = "Sydney Windows 11 lab workstation" },
    @{ Name = "MEL-WIN11-01"; Path = $MelbourneWorkstationsOU; Description = "Melbourne Windows 11 lab workstation" },
    @{ Name = "LAB-SRV01";    Path = $ServersOU;              Description = "Lab member and file server" },
    @{ Name = "LAB-APP01";    Path = $ServersOU;              Description = "Lab application server" }
)

foreach ($Computer in $Computers) {
    if (-not (Get-ADComputer `
        -Filter "Name -eq '$($Computer.Name)'" `
        -ErrorAction SilentlyContinue)) {

        New-ADComputer `
            -Name $Computer.Name `
            -SamAccountName "$($Computer.Name)$" `
            -Path $Computer.Path `
            -Description $Computer.Description `
            -Enabled $true
    }
}
Don't drop the trailing dollar sign

The $ at the end of -SamAccountName "$($Computer.Name)$" is required — that trailing dollar is how AD marks an account as a computer rather than a person.

09

Group Policy — the rules pushed out to machines

This is why the OUs in Part 4 were worth building.

A GPO is a bundle of settings. You link it to an OU, and every computer or user inside that OU picks it up automatically — at boot or logon, then re-checked roughly every 90 minutes.

Three steps, always this order

1. Create — New-GPO, an empty bundle.
2. Link — New-GPLink, decides who gets it.
3. Fill — Set-GPRegistryValue, what it does.

A GPO with no link does nothing. A link with no settings does nothing. You need all three.

Name it once and reuse. The convention LAB - <what it does> keeps a long GPO list readable — and fill in -Comment, because a GPO called "Baseline" with no description is useless to whoever inherits it.

$WorkstationGPO = "LAB - Workstation Security Baseline"

if (-not (Get-GPO `
    -Name $WorkstationGPO `
    -ErrorAction SilentlyContinue)) {

    New-GPO `
        -Name $WorkstationGPO `
        -Comment "Basic workstation security settings for the AD lab"
}

Link it to the Workstations OU, so machines in both Sydney and Melbourne pick it up — links flow down into child OUs.

if (-not (Get-GPInheritance `
   -Target $WorkstationsOU).GpoLinks |
   Where-Object DisplayName -eq $WorkstationGPO) {

   New-GPLink `
       -Name $WorkstationGPO `
       -Target $WorkstationsOU `
       -LinkEnabled Yes
}
This if-statement does not work

The brackets are misplaced. -not is applied to .GpoLinks first, and the true/false that comes out is then piped into Where-Object, which can't match anything. The result is always empty, empty counts as false, so New-GPLink never runs. No error — just no link, and the GPO does nothing at all.

The whole pipeline has to sit inside -not ( ):

if (-not ((Get-GPInheritance -Target $WorkstationsOU).GpoLinks |
    Where-Object DisplayName -eq $WorkstationGPO)) {

Check afterwards with Get-GPInheritance -Target $WorkstationsOU. If the link isn't listed, this is why.

The settings. Set-GPRegistryValue writes a registry key into the GPO; every machine the GPO applies to then gets that key. HKLM means a computer setting — it applies no matter who signs in.

# turn off AutoRun on every drive type. 255 covers all drive
# letters including USB — a classic malware entry point.
Set-GPRegistryValue `
   -Name $WorkstationGPO `
   -Key "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer" `
   -ValueName "NoDriveTypeAutoRun" `
   -Type DWord `
   -Value 255

# the other half — AutoPlay for non-volume devices (phones,
# cameras, MTP gear), which the setting above doesn't cover.
Set-GPRegistryValue `
   -Name $WorkstationGPO `
   -Key "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer" `
   -ValueName "NoAutoPlayfornonVolume" `
   -Type DWord `
   -Value 1

The logon banner. Caption and Text are a pair — set only one and no banner appears at all.

Set-GPRegistryValue `
   -Name $WorkstationGPO `
   -Key "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System" `
   -ValueName "LegalNoticeCaption" `
   -Type String `
   -Value "LAB.LOCAL Authorised Access Only"

Set-GPRegistryValue `
   -Name $WorkstationGPO `
   -Key "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System" `
   -ValueName "LegalNoticeText" `
   -Type String `
   -Value "This computer is part of an authorised Active Directory training environment."
The banner is a legal control, not a technical one

It stops nobody. What it does is remove the "I didn't know I wasn't allowed on here" defence, which is why most hardening standards expect one.

Useful checks once this part is done.

Get-GPO -All | Select-Object DisplayName, GpoStatus
Get-GPInheritance -Target $WorkstationsOU
Get-GPOReport -Name $WorkstationGPO -ReportType Html -Path "C:\gpo.html"

gpupdate /force        # on the CLIENT, to pull policy down now

9b · A second GPO, for users this time

The GPO above used HKLM — a computer setting, applied to the machine whoever signs in. This one uses HKCU, a user setting that follows the person to whatever machine they use. That difference is what decides which OU you link it to.

Same create-and-link shape, pointed at the users OU instead.

$UserGPO = "LAB - User Session Security"

if (-not (Get-GPO -Name $UserGPO -ErrorAction SilentlyContinue)) {
    New-GPO `
        -Name $UserGPO `
        -Comment "User session and screen lock settings"
}

New-GPLink `
   -Name $UserGPO `
   -Target $UsersOU `
   -LinkEnabled Yes
Missing dollar sign

In the class notes this was written UserGPO = "LAB - User Session Security" with no $. PowerShell reads that as a command called UserGPO, so $UserGPO stays empty and every command after it quietly targets nothing.

Screen lock — three settings that only work as a set. All three are -Type String, even the number, because the registry stores them as text.

# ScreenSaveActive    turn it on at all
# ScreenSaverIsSecure require the password to get back in  <- the security bit
# ScreenSaveTimeOut   idle seconds before it kicks in (600 = 10 minutes)
Set-GPRegistryValue `
   -Name $UserGPO `
   -Key "HKCU\Software\Policies\Microsoft\Windows\Control Panel\Desktop" `
   -ValueName "ScreenSaverIsSecure" `
   -Type String `
   -Value "1"

File share & NTFS permissions

The "P" of AGDLP finally arriving — the actual permission.

Everything up to now lived inside AD. This is the thing AD has been protecting: a real folder on the server's disk. Order matters — folder first, then break inheritance, then assign the DL groups.

-Force means don't error if it already exists, and create any missing parent folders on the way.

$FinancePath = "C:\LabShares\Finance"

New-Item `
   -Path $FinancePath `
   -ItemType Directory `
   -Force

icacls is the built-in tool for NTFS permissions — a legacy .exe, but still the standard way to do this.

icacls $FinancePath /inheritance:d
Why :d and not :r

By default a folder inherits permissions from its parent, so anything set higher up flows in. /inheritance:d disables inheritance but copies the current permissions down first, so they become explicit on this folder.

/inheritance:r removes them instead — and can lock you out of your own folder. Reach for :d.

Next step, once the DL groups from Part 7 actually exist: grant them. (OI)(CI) means apply to files and subfolders too; M is Modify, RX is Read + Execute.

icacls $FinancePath /grant "DL-FinanceShare-Modify:(OI)(CI)M"
icacls $FinancePath /grant "DL-FinanceShare-Read:(OI)(CI)RX"

Account lifecycle

What actually happens to accounts day to day.

The golden rule for a leaver: disable and move, never delete. Deleting destroys the SID — and every file permission and group membership in the domain points at that SID, not at the name. Recreating “the same” account gives you a new SID and none of the old access comes back.

A contractor finishes: turn the account off, file it in the parking OU, and record why.

Disable-ADAccount -Identity "alex.contractor"

Get-ADUser "alex.contractor" |
    Move-ADObject -TargetPath "OU=Disabled Users,$UsersOU"

Set-ADUser `
    -Identity "alex.contractor" `
    -Description "Contract completed; account disabled for lab exercise"

An expiry date is better than remembering to disable them yourself.

Set-ADAccountExpiration `
    -Identity "alex.contractor" `
    -DateTime (Get-Date).AddDays(30)

Clear-ADAccountExpiration -Identity "alex.contractor"

Password reset. -Reset means “just set it, don’t ask for the old one” — the helpdesk operation, as opposed to a user changing their own.

Set-ADAccountPassword `
    -Identity "sarah.malik" `
    -Reset `
    -NewPassword $NewPassword

# then force a change at next logon, so you never know it
Set-ADUser -Identity "sarah.malik" -ChangePasswordAtLogon $true
Locked out is not the same as disabled

Locked out means too many wrong passwords; it clears itself after the lockout window. Disabled means an admin deliberately turned it off. Different problems, different fixes.

Find them in bulk rather than one at a time.

Unlock-ADAccount -Identity "sarah.malik"

Search-ADAccount -LockedOut
Search-ADAccount -UsersOnly -AccountDisabled

Delegation

Let the helpdesk reset passwords without being Domain Admins.

This is least privilege in practice: give the smallest right that does the job. The group was created back in Part 7 — this is where it finally gets used.

Add the helpdesk person, then read the ACL on the OU to see who can do what to it.

Add-ADGroupMember `
    -Identity "GG-Helpdesk-Password-Reset" `
    -Members "daniel.nguyen"

dsacls "OU=LAB-Users,$DomainDN"

# filtered, because the full output is enormous
dsacls "OU=LAB-Users,$DomainDN" |
    Select-String "GG-Helpdesk-Password-Reset"
These commands don't grant the right

They add the member and read the result. Granting the delegation itself is done in the Delegation of Control wizard in ADUC (right-click the OU), or with dsacls /G. If Select-String returns nothing, that step hasn't been done yet.

gMSA

A service account whose password nobody ever knows.

Active Directory manages the password itself: 120 characters, rotated every 30 days, never typed by a human. It replaces the old habit of running a service as a normal account with the password sitting in a config file.

Run the root key once, and only if you don't have one

Check first with Get-KdsRootKey. Production uses -EffectiveImmediately; the backdated version below exists because it normally waits 10 hours to replicate, which a single-DC lab doesn't need to sit through.

Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10))

The group holds computers, not people — that’s the whole idea. The trailing $ makes it a machine account name, same rule as Part 8.

$CurrentComputer = "$env:COMPUTERNAME$"

Add-ADGroupMember `
    -Identity "GG-gMSA-WebHosts" `
    -Members $CurrentComputer

Create the account. AES128/AES256 only — the older RC4 is weak.

New-ADServiceAccount `
    -Name "gmsa-webapp" `
    -DNSHostName "gmsa-webapp.$DomainName" `
    -PrincipalsAllowedToRetrieveManagedPassword "GG-gMSA-WebHosts" `
    -KerberosEncryptionType AES128, AES256

# then, ON the web host itself:
#   Install-ADServiceAccount -Identity "gmsa-webapp"
#   Test-ADServiceAccount    -Identity "gmsa-webapp"

Querying & troubleshooting

LDAP filters, and finding out who you actually are.

-Filter is PowerShell syntax. -LDAPFilter is raw LDAP: uglier, far more powerful, and it’s what AD actually speaks.

Reading an LDAP filter

(attribute=value) is one condition. (&(a=1)(b=2)) is AND — note the & goes first, not between. (|...) is OR, (!...) is NOT.

Who am I, really? /user shows your SID, /groups every group in your token. klist shows your Kerberos tickets — stale ones explain a lot of odd “access denied” behaviour.

whoami
whoami /user
whoami /groups

klist

# which DC am I actually talking to?
nltest /dsgetdc:$DomainName

Everyone in Finance. Reads as: is a person AND is a user AND department is Finance.

Get-ADUser `
        -LDAPFilter "(&(objectCategory=person)(objectClass=user)(department=Finance))" `
        -SearchBase $UsersOU `
        -Properties Department |
    Select-Object Name, SamAccountName, Department
The three lines that wouldn't run

All three LDAP queries in the notes had curly “ ” quotes from a Word or Teams paste. PowerShell only accepts straight " and throws a parse error on the curly ones. It is the single most common paste problem — if a pasted command fails for no visible reason, retype the quotes first.

Every enabled user. That long number is the LDAP bitwise-AND matching rule: bit 2 of userAccountControl is the “disabled” flag, and (!...) inverts it. Nobody remembers this — look it up each time.

Get-ADUser `
    -LDAPFilter "(&(objectCategory=person)(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))" `
    -SearchBase $UsersOU
Why the SID matters more than the name

The SID is what permissions are actually written against. That is why deleting an account and recreating it with the same name does not restore its access — and why Part 11 says disable, never delete.

Auditing

If it isn't on before an incident, the evidence doesn't exist.

Auditing is off by default for most of what matters. Turn on success and failure: failures show attacks being attempted, successes show what actually happened.

Check what’s on, then enable the identity subcategories.

auditpol /get /category:*

auditpol /set /subcategory:"User Account Management"   /success:enable /failure:enable
auditpol /set /subcategory:"Security Group Management" /success:enable /failure:enable
auditpol /set /subcategory:"Logon"                     /success:enable /failure:enable

Make something happen, then go find it. These are the event IDs worth memorising.

#  4720 user created   4722 enabled   4725 disabled   4726 deleted
#  4728/4729 global group member added/removed
#  4732/4733 local  group member added/removed
Get-WinEvent -FilterHashtable @{
        LogName   = "Security"
        StartTime = (Get-Date).AddMinutes(-30)
        Id        = 4720, 4722, 4725, 4726, 4728, 4729, 4732, 4733
    } |
    Select-Object TimeCreated, Id, Message |
    Format-List
Two mistakes in this section

-Members "audit. Test" has a stray space and the wrong case, so it can't find the account. And $InitialPassword is reused here, silently overwriting the secure string from Part 5 with a plaintext one — give it its own variable name.

Privileged access review

Who has the keys, and which accounts are quietly weak.

The single most valuable recurring check in AD. -Recursive matters enormously: someone can be a Domain Admin through three levels of nested groups and never appear in a direct membership list.

The nine groups worth reviewing. The bottom four surprise people — each has a path to full control, which is exactly why attackers look there.

$PrivilegedGroups = @(
    "Domain Admins", "Enterprise Admins", "Schema Admins",
    "Administrators", "Account Operators", "Server Operators",
    "Backup Operators", "Group Policy Creator Owners", "DnsAdmins"
)

foreach ($Group in $PrivilegedGroups) {
    Write-Host "`n=== $Group ===" -ForegroundColor Cyan

    Get-ADGroupMember -Identity $Group -Recursive -ErrorAction SilentlyContinue |
        Select-Object Name, SamAccountName, ObjectClass
}
Calculated properties

The export version wraps each row in @{Name=;Expression=} — a calculated property. It adds a column saying which group the row came from, which the printing loop above shows on screen and then throws away.

Account hygiene. The last one should always come back empty.

Search-ADAccount -UsersOnly -AccountExpired
Search-ADAccount -UsersOnly     -AccountInactive -TimeSpan 90.00:00:00
Search-ADAccount -ComputersOnly -AccountInactive -TimeSpan 90.00:00:00

# passwords that never expire - usually old service accounts nobody owns
Get-ADUser -Filter { PasswordNeverExpires -eq $true } -Properties PasswordNeverExpires |
    Select-Object Name, SamAccountName

# accounts needing NO password at all
Get-ADUser -Filter { PasswordNotRequired -eq $true } -Properties PasswordNotRequired |
    Select-Object Name, SamAccountName

Domain controller health

What you run first when something is broken and you don't know what.

Check the clock early

Kerberos rejects any ticket where the clocks differ by more than five minutes. A DC with bad time breaks all authentication domain-wide — and the symptom, “access denied”, looks nothing like a clock problem.

dcdiag runs about thirty tests against the DC. The DNS one is worth running on its own, because DNS causes most AD faults.

dcdiag
dcdiag /v
dcdiag /test:dns /v

SYSVOL and NETLOGON are where Group Policy and logon scripts actually live. If these are missing, policy silently stops applying everywhere.

Get-SmbShare -Name SYSVOL, NETLOGON

# ...and can they be reached? Both should return True.
Test-Path "\\\\$DomainName\\SYSVOL"
Test-Path "\\\\$DomainName\\NETLOGON"

The six services a DC cannot work without. All should be Running.

#  NTDS the AD database  ·  DNS  ·  Netlogon secure channel + SYSVOL
#  KDC Kerberos tickets  ·  ADWS what the PS module talks to  ·  DFSR SYSVOL replication
Get-Service NTDS, DNS, Netlogon, KDC, ADWS, DFSR |
    Format-Table Name, Status, StartType

w32tm /query /status
w32tm /query /source
w32tm /query /configuration

AD Recycle Bin

Delete something, then get it back intact.

Deleting an AD object normally leaves a tombstone — a husk with almost every attribute stripped out. The Recycle Bin keeps the object intact, so a restore brings back its attributes, its group memberships, and the same SID. That last part is why file permissions still work afterwards.

Enabling it is permanent

There is no supported way to turn the Recycle Bin back off once it's on. It is still the right call — just know it's a one-way door before you run it.

Check, enable forest-wide, check again. Empty EnabledScopes means it isn’t on yet.

Get-ADOptionalFeature -Filter "Name -eq 'Recycle Bin Feature'" |
    Select-Object Name, EnabledScopes

Enable-ADOptionalFeature `
    -Identity "Recycle Bin Feature" `
    -Scope ForestOrConfigurationSet `
    -Target $Forest.Name

Prove it on a disposable account. Note the ObjectGUID first — it’s the one identifier that survives deletion.

Remove-ADUser -Identity "recycle.test" -Confirm:$false

# deleted objects are invisible to Get-ADUser - you need Get-ADObject.
# LastKnownParent is the OU it came from, which is what makes the
# restore land back in the right place.
Get-ADObject `
        -Filter "SamAccountName -eq 'recycle.test'" `
        -IncludeDeletedObjects `
        -Properties SamAccountName, LastKnownParent |
    Format-List Name, SamAccountName, Deleted, LastKnownParent, ObjectGUID

Get-ADObject -Filter "SamAccountName -eq 'recycle.test'" -IncludeDeletedObjects |
    Restore-ADObject

Backup

A domain controller without a tested backup is a single point of failure for the whole domain.

Two different jobs, often confused

System state is the AD database itself — NTDS.dit, SYSVOL, the registry. It's what you restore from when the DC dies.

GPO backup is just the policy objects. Far more common in practice: someone edits a GPO, breaks something, and you roll back that one GPO without touching the rest of the domain.

Check the target volume first — a system state backup of a lab DC runs 8–15 GB, and -backuptarget must be a volume that exists and isn't the system drive.

Get-Volume |
    Format-Table DriveLetter, FileSystemLabel, FileSystem, SizeRemaining, Size

wbadmin start systemstatebackup -backuptarget:E: -quiet

wbadmin get status
wbadmin get versions

Back up every GPO. The -Comment is stamped into the backup manifest — it's how you tell three backups apart six months later.

$GPOBackupPath = "C:\LabBackups\GPO"

New-Item -Path $GPOBackupPath -ItemType Directory -Force

Backup-GPO -All -Path $GPOBackupPath -Comment "Full lab GPO backup $(Get-Date)"

# each GPO lands in its own GUID-named folder
Get-ChildItem -Path $GPOBackupPath -Recurse

# to restore one later:
#   Restore-GPO -Name "LAB - Workstation Security Baseline" -Path $GPOBackupPath
Two things the notes got wrong here

wbadmin start systemstatebackup appeared twice in a row — running it twice wastes an hour and a lot of disk. And -backuptarget:E: assumes an E: volume exists; on a machine without one it simply fails.

CSV reports

Turning the domain into files you can hand over, diff against last month, or open in Excel.

Every GPO's full settings as one browsable HTML report — this is what you attach to a change request.

Get-GPOReport -All -ReportType Html -Path "C:\LabReports\All-GPOs.html"

Users. LastLogonDate and PasswordLastSet are the two columns that turn a list into an audit.

Get-ADUser `
        -Filter * `
        -SearchBase $UsersOU `
        -Properties Department, Title, Office, Enabled, LastLogonDate, PasswordLastSet |
    Select-Object Name, SamAccountName, Department, Title, Office, Enabled,
        LastLogonDate, PasswordLastSet, DistinguishedName |
    Export-Csv -Path "C:\LabReports\AD-Users.csv" -NoTypeInformation

# computers - OperatingSystem exposes machines nobody has patched in years
# groups, and OUs with ProtectedFromAccidentalDeletion, follow the same shape
Always use -NoTypeInformation

Without it, Export-Csv writes a #TYPE System.Management.Automation... line at the top, which Excel shows as a junk first row.

Group membership, flattened to one row per group-member pair — the shape you actually want for reviewing access.

$GroupMembershipReport = foreach ($Group in (Get-ADGroup -Filter * -SearchBase $GroupsOU)) {

    $Members = Get-ADGroupMember -Identity $Group -ErrorAction SilentlyContinue

    if ($Members) {
        foreach ($Member in $Members) {
            [PSCustomObject]@{
                GroupName        = $Group.Name
                MemberName       = $Member.Name
                MemberType       = $Member.ObjectClass
            }
        }
    }
    else {
        [PSCustomObject]@{ GroupName = $Group.Name; MemberName = "<No members>" }
    }
}
Why the else branch matters

An empty group still gets a row, so it appears in the report instead of silently vanishing. Empty security groups are worth seeing — they're usually leftovers nobody cleaned up, and they accumulate.

Audit account

A read-only account for assessment tooling, so you never run a scanner as Domain Admin.

AD assessment tools — ADRecon, PingCastle, BloodHound — only need to read the directory. Running them as Domain Admin is the lazy habit that turns an audit into an incident: the tool's credentials become the most valuable thing on the network. A standard domain user can already read most of AD, which is the whole point of this account.

No groups, no rights beyond Domain Users — and it still works.

New-ADUser `
    -Name "ADRecon Audit User" `
    -SamAccountName "adrecon.audit" `
    -UserPrincipalName "adrecon.audit@$DomainName" `
    -Description "Standard read-only account for authorised AD assessments" `
    -Path $AuditAccountOU `
    -AccountPassword $ADReconPassword `
    -Enabled $true `
    -ChangePasswordAtLogon $false

# confirm it is ONLY in Domain Users. Anything else here means the
# account is over-privileged and should not be handed to a scanner.
Get-ADPrincipalGroupMembership "adrecon.audit" |
    Select-Object Name, GroupScope
The one place ChangePasswordAtLogon $false is correct

Everywhere else in this script that flag is $true, deliberately. Here it's $false because a tool cannot answer a password-change prompt — which is exactly why the account must carry no privileges to compensate.

The worst bug in the whole set was here

The notes redefined $UsersOU at this point to "OU=Information Technology,OU=LAB-Users,$DomainDN" — silently repointing it from LAB-Users to one department. Every later command using it would target the wrong OU, and nothing would error. It now uses its own $AuditAccountOU.
